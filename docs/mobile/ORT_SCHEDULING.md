# 真机原始分轨窗口超时：调度诊断与修正

2026-10-12，接续 [分轨准备队列](STEM_QUEUE_INTEGRATION.md)。
**PASS_DEVICE_WINDOW / FULL_AUTOMIX_IN_PROGRESS**。仅独立 QA，个人 App 保持 mobile.28。

## 问题与证据

前一阶段同一 iPhone XS Max / iOS18.7.10 在 Folia 宿主内运行原始 30 秒音乐 tail 时，
约 60.27 秒返回 `ort-timeout`；约 40 秒起热状态为 serious。
旧独立探针曾在约 41.4 秒完成，但当时调度和负载环境不同，不能直接替代失败记录。

按优先级检查的假设为调度优先级、宿主／热负载、模型加载／核验及编译选项。
发现独立探针用 `QOS_CLASS_USER_INITIATED`，Folia 串行模型队列用 `.utility`。
两者 ORT 1.30.0 的 iPhone 运行库逐字节一致，SHA256 为
`1a68904a1513ed02f4e3a7ea1162b1d341178b6df7a511a007062922765c88ec`。
模型、2 个计算线程、串行执行、关闭 CPU arena 和 memory pattern 均未变化。
独立探针 C++ 优化为 O2，App 为 Os；本轮没有改变编译优化，避免同时改变多个条件。

在同一 Folia QA 宿主中，使用同一原始音乐输入和模型，依次以显式 utility / userInitiated 调度，
首段完成后立即取消，不把这项探针算成完整窗口通过。两个阶段记录的热状态均为 fair（1）：

| 测量 | utility，实际 QoS 17 | userInitiated，实际 QoS 25 |
|---|---:|---:|
| Session 加载 | 1.470 秒 | 0.463 秒 |
| 首段完成并取消的运行阶段 | 6.560 秒 | 3.264 秒 |
| 整个探针阶段 | 8.770 秒 | 3.749 秒 |

运行阶段包含取消响应，不是纯内核计时；同一顺序的一次对比也不是统计基准。
第二次加载还可能受文件缓存影响，所以不能把加载差异全部归因于 QoS。
运行阶段的差异支持调度假设，随后必须用真实队列完整窗口验证修正。

## 最小修正

- 将现有 `NativeORTInference` 全局串行队列改为 `.userInitiated`，用于当前／下一首的有期限分析。
  保持低于音频实时渲染的调度级别；不新增线程池、不并行加载两个模型。
- 原 60 秒执行期限、模型核验、不可变快照、取消和热／内存保护保持原样。
  没有缩短 30 秒窗口，没有转换／量化模型，也没有更换运行库。
- `FoliaORTJob` 增加按需读取的纯数值诊断：实际线程 QoS、Session 加载与运行阶段耗时、
  已完成段数，以及主 App 进程 physical footprint／峰值。运行计数用原子变量，失败和取消也记录运行耗时。
  生产没有自动日志、采样定时器或 Web 桥接接口，不记录模型路径、音频、URL 或凭据。
- QA 增加首段调度对比；完整队列用例增加四轨原参考对照。
  手机沿用既有跨设备容差：量化 PCM 最大差不超过 1；不要求跨设备位级一致。

## 修正后的真机结果

`device-window.xcresult`：完整歌曲解码、30 秒 tail、原 HTDemucs、原四轨整理和队列缓存复用通过。
推理与整理用时 **42.7967 秒**，整个测试 **44.212 秒**。
模型和音频仍为前一阶段相同摘要；起点 4,541,768 帧、窗口 1,323,000 帧，四轨缓存 21,168,000 字节。
人声退出点为原值 `23.650000000000002`；vocals／drums／bass／other 的量化 PCM 最大差均为 1，gain 相同。
取消并重新选择同一歌曲直接复用同一个窗口对象，没有再次推理。

主 App 进程峰值 **1,293,585,360 字节，约 1.20 GiB**；10／20／30 秒采样为 fair，40 秒为 serious。
该数字不包含独立 WebContent 进程，也不代表整个 App 总内存；没有同时播放歌曲、运行歌词动画或测长期稳态。
此用例直接使用分轨协调器，未接系统热通知；实际播放器的 serious 热保护可能更早取消任务。
因此本轮解决了当前隔离调用的超时，**未证明播放状态下能完成分轨或适合持续启用**。
